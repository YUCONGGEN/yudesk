# RTT 与负载排队优化（2026-09-08）

本轮优化已实现于桌面和 Android 共用 Go 通信代码，并随 `p2p-20260908.1` 部署至官网（Android preview.3）。上一轮未完成的 Windows 窗口改动不属于本次传输改动。需要双方升级才能启用交错传输，旧端仍可连接但不获得该功能。下文保留开发阶段的原始测量，不作为发布后的公网性能承诺，最新部署见 [发布状态](RELEASE_STATUS.md)。

## 改动与边界

- 认证阶段双向协商 `interleaveV1`。大数据按 8KiB 分片，短消息可在分片边界发送，不再必须等整张大图完成。输入确认、帧 ACK、心跳、短声音消息共用优先级；最多连续优先 8 次，然后给等待的大数据一次机会，避免长期饥饿。
- 仍是端到端加密 TCP，不是独立 UDP 控制通道；已经进入 TCP/运营商队列的数据以及丢包重传，不能靠应用分片绕过。中转拓扑、监听端口、证书、PIN 和审批权限不变。
- 按现有画面带宽预算分散大块发送，减少一次灌入发送缓冲的大突发。控制消息不被限速计时器锁住；零带宽上限仍表示不限速。文件与画面共享大数据写入预算。用户设置的带宽高于实际可用带宽时，仍可能出现底层排队。
- Agent 为大文件响应和短响应分别设置有界发送队列，避免文件占住唯一响应 worker。每方向最多组装一条分片大消息，长度仍受原 32MiB 上限约束；错误偏移、重复开始、异常长度和未协商分片拒绝。
- 连接内复用协议与加密缓冲；加密层保持 v1 字节格式，不使用全局明文池。完整消费后清除解密缓冲，失败的记录不重用 nonce，序列号不回绕。
- 安卓取消画面流时，已开始的帧使用会话级、有超时的写上下文完成；会话关闭仍中止传输。避免切换设置时留下半条消息。
- **没有修改 RTT 统计口径**。页面继续展示实际请求到响应的耗时，不扣掉排队时间、不把历史最小值伪装成当前 RTT。

## 可复现负载实验

### 协商后的帧格式

原来的 8 字节前缀仍使用大端序。`headerSize` 的最高位仅在已协商的分片包中置一，其余位为扩展头长度；`dataSize` 为本片数据长度，限制为 1～8192 字节。扩展头前 9 字节依次为 flags（1 字节）、offset（4 字节）、total（4 字节）。flags 的 bit0 表示首片、bit1 表示末片，其他位必须为零；首片的 9 字节后包含原完整 JSON 消息头，续片不得重复 JSON 头。

同方向同时只允许一条大消息在组装，offset 必须连续、total 必须一致，末片必须恰好结束。普通消息可以穿插；上层只在大消息完整后取得其 Data，不把不完整图片交给解码器。未发出任何分片的排队取消不损坏会话；已经发出部分分片后若写入失败/取消，则关闭连接，不尝试复用半条消息。

### 测量结果

命令：`go test ./internal/protocol -run '^$' -bench BenchmarkLoadedProbe -benchtime=5x -count=1`。

同机 Go 1.27.1/Linux/i5-7300HQ；每档 5 次。开始发送 256KiB 画面时发起真实协议 ping/reply，在同一条无缓存、限速的测试连接上计时。限速使用绝对字节时钟，避免每个分片单独睡眠的计时误差累计。每次都继续读完并逐字节核对完整画面，不通过丢弃画面得到较低数值。

| 模拟有效带宽 | 原串行 P50 / P95 | 交错传输 P50 / P95 |
| --- | --- | --- |
| 2 Mbps | 1051 / 1051 ms | 35.53 / 43.22 ms |
| 8 Mbps | 264.1 / 264.7 ms | 10.47 / 10.56 ms |

这是刻意在大帧起始处触发请求的**应用排队实验，不是公网 RTT 或操作到显示器出光的实测**。样本少，P95 使用 nearest-rank（5 个样本时等于最大值），不代表长期尾延迟。整次帧传输平均耗时约 1051→1053ms、264.5→264.9ms，载荷没有省略。真实 TCP 缓冲、拥塞窗口、声音、丢包和并发网络流量会改变结果。

加密 record 微基准（3 次中位数）：64KiB 写入约 93.75→56.63μs，读取约 149.91→80.55μs；代表大小的稳态读写为 0 B/op、0 allocs/op。这只表示记录处理开销，不表示整个应用零分配或网络 RTT 同比例下降。

### Windows 输入到画面联调

在同一开发机上，以 Git `99903b884e87c03b86582586444f2e427b3c59e8` 为基线构建旧端，再从该基线仅叠加本轮传输代码构建候选端，未混入尚未完成的 Windows 窗口实验。两组使用相同测试脚本、独立临时身份/数据库、本地中转和 headless Chrome，每组 55 个计入统计的样本，不额外注入网络延迟。

输入通过真实协议发送，测试 Agent 仅修改合成画面的像素；浏览器等待相应像素出现在 canvas 后计时。没有采集真实桌面、注入系统键鼠或锁屏。这覆盖输入通道、画面返回和浏览器 canvas 更新，但不包括真实屏幕扫描出光、真实应用响应和公网线路。

| 同机版本 | 输入到 canvas P50 | P95 | 最大值 | 空闲后首次唤醒 |
| --- | --- | --- | --- | --- |
| 基线 | 97.2 ms | 172.6 ms | 190.5 ms | 84.0 ms |
| 仅传输优化 | 87.7 ms | 142.2 ms | 166.0 ms | 133.4 ms |

这是单轮配对结果，不能据此承诺普遍或长期收益。候选版的空闲唤醒反而更慢；测试后的 CPU 负载单次快照为 100%（i5-7300HQ），尚不能确定具体负载来源或将波动全部归因于它。后续需要在稳定负载和真实两端环境下重复测试。没有拿历史低负载成绩与当前结果直接比较，也没有把负载探针的约 10ms 等同于画面延迟。

同时修正了联调脚本的退出检查竞态：关闭最后一个浏览器连接已经触发 Viewer 自动退出，脚本不再随后向已退出的 HTTP 服务请求退出，而是直接严格等待并验证 Viewer 与合成 Agent 进程退出。基线和候选端均通过像素匹配及进程退出检查。

## 当前线路的参考测量

本开发机对 `www.yucg.cn:8233` 做 6 次直接 TCP 建连：391.89、96.74、148.58、107.92、72.59、83.84ms。首个样本包含冷启动开销；其余中位数 96.74ms。建连还包含 DNS/本机调度等成本，**不是纯线路 ping，也不是控制端—中转—被控端完整会话 RTT**；无法据此断言每位用户的网络延迟。

地理距离、接入网络、路由和实际可用带宽给 RTT 设定底限。只改客户端不能保证个位数毫秒或零延迟。进一步判断线路需要两端城市、接入方式和真实会话样本，不会擅自新增付费中转节点或改变用户要求的中转模式。
