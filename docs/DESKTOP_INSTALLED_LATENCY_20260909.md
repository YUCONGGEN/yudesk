日期：2026-09-09。以下保留早期 Windows 候选与性能基线，**不是最终跨平台下载包的校验记录**；后续整合了 Unix 原生窗口、安装包、兼容接口及 Android 优化，最终包和部署状态见 [跨平台集成](ALL_PLATFORM_RELEASE_20260909.md)、[发布状态](RELEASE_STATUS.md)。

历史候选文件：`dist/windows-2.0.0-installed-20260909/YuDesk-2.0.0-windows-amd64.exe`，16,629,760 字节。

SHA-256：`3b25e756b0802ffdf8344adf1a00dfdd1490ada6ebaaaff8e71e36bfaa9b7c14`。

最终交付的同一可执行文件已跑通隔离统一端启动、重复启动复用与退出回归。最终原生宿主在通过 Windows vet 后再次跑完 5 轮窗口转换；macOS arm64、Linux amd64 编译通过，不等于这些平台的真机窗口验收。

## 修复内容

- 正常启动默认推荐安装版；应用内明确确认后才触发 Windows 管理员授权。取消可以便携运行，选择保存在本机。隔离测试、命令行无界面和自定义身份目录不会自动弹出安装请求。
- 安装等待真实辅助进程退出及服务达到 Running；失败不会自动切换。切换前比较当前程序与安装目录程序 SHA-256，避免最新下载包又启动旧安装版。哈希按文件身份、时间、大小缓存，避免状态轮询反复读取可执行文件。
- Windows 使用无系统标题栏的原生宿主，按 Chromium 真实网页边界布局，非固定像素裁剪。隐藏保留网页状态，复用原窗口；最小化、内部关闭按钮保持原语义。专属浏览器 Job Object 退出时清理，不结束用户其他浏览器。
- OS 输入从协议读取线程移到单个独立工作协程：队列至多 64 条，每条参数至多 64 KiB。仅合并相邻单点悬停位置，保留拖动轨迹、按键、滚轮、释放及需要回应的旧版请求。积压超限安全结束本次会话并释放本次持有的按键，不能无限积压或随意丢弃松开事件。
- 画面尺寸通过原子值发布，截图线程不再等待系统输入锁；断开取消剩余批次，等待正在执行的输入后释放按键。保留上轮“会话失败返回首页，不退出整个应用”和浏览器监控重连修复。
- Canvas 请求低延迟呈现提示；不支持的浏览器继续普通 2D 绘制。没有把此提示当作降低公网 RTT 的保证，也没有缩小 SCTP 接收窗口或关闭拥塞控制。

## 验证

- Linux 全量 `go test ./...`、`go vet ./...`；agentapp、viewerapp、peerpath、relay、protocol、stream 的 race 测试。
- Windows 安装版本比较、同尺寸文件替换缓存失效、ShellExecuteEx 结构布局、等待服务启动的单元测试；不可信程序不能访问特权服务。
- Windows 模拟慢 OS 输入时，协议 ping 和截图尺寸更新不被阻塞；队列合并、拖动次序、溢出、取消及退出清理回归。
- 无标题栏原生窗口连续 5 轮：页面往返、最小化/恢复、最大化/恢复、尺寸变化、隐藏/显示及真实 WM_CLOSE。独立浏览器作业清理 3 轮。测试窗口不注入真实系统输入。
- 浏览器集成：860×562 紧凑设置、折叠授权、无页面滚动、默认安装、拒绝授权、安装失败不重启、成功后切换、旧版不可切换、自定义提示、设备列表、PIN 轮换、60 秒确认连接与结束控制返回首页。

当前电脑仍有旧安装版在运行。本轮没有替换它、安装/卸载实际服务或锁屏；真实管理员安装和外网两端体验仍需在新包上验收。模拟服务接口测试不等于完成真实安装验证。

## 延迟测试方法与限制

`TestNativeVisualLatency` 使用合成桌面与正常会话、编码、HTTP/Canvas 通道，鼠标事件只改变合成图像，不操作真实电脑。中转每个方向注入 50 ms 传播时间，测量输入到匹配像素的时间，不以请求成功代替画面出现。每轮 60 次，跳过 5 次预热，另测空闲唤醒。

本轮发现旧基准允许本机 P2P 绕过注入延迟，显示“100ms 场景”但实测 RTT 只有 2.8 ms。因此测试辅助端现在强制 ICE 尝试超时回退，并断言实际通道为 relay、实测 RTT 不低于注入值。这只改变测试辅助程序，不关闭正式程序的 P2P。

串行对比（每行一轮，单位 ms；旧组为修复前输入代码与普通 Canvas，新组为独立输入队列和低延迟 Canvas 提示）：

| 构建 | 轮次 | 实测 RTT | 输入到像素 P50 | P95 | 最大值 |
| --- | --- | --- | --- | --- | --- |
| 旧 | 1 | 102.6 | 119.0 | 139.6 | 266.5 |
| 旧 | 2 | 101.2 | 119.2 | 187.3 | 221.3 |
| 旧 | 3 | 102.8 | 119.0 | 135.0 | 135.5 |
| 新 | 1 | 105.1 | 120.0 | 189.6 | 253.8 |
| 新 | 2 | 120.9 | 121.7 | 170.1 | 202.4 |
| 新 | 3 | 101.2 | 119.7 | 137.1 | 157.4 |

结论：未测出正常、无输入阻塞的 100 ms 链路上平均画面响应显著改善；不能宣传从 100 ms 降为几十毫秒。独立输入的收益由阻塞故障回归验证：人为阻塞 OS 输入时，截图尺寸更新和 ping 仍能完成，而不是一同等待。上表反映本机测试调度的波动，不是互联网两台设备的实测。

并行启动窗口测试时，新版曾测到 P95 330–466 ms、最大 564–708 ms；这表明本机资源争抢仍会产生长尾，不能宣传任何负载下都不卡。正式对比需要串行运行、避免其他构建与浏览器启动。此模拟不覆盖运营商路由、真实丢包、带宽拥塞、显卡采集或物理显示器扫描延迟。

物理网络往返约 100 ms 时，软件不能保证远程画面零延迟。应在两端都更新后查看实际 P2P/中转状态；打洞失败仍安全回退到中转。本轮主要消除软件阻塞与旧版复用问题，不能把原有 P2P 功能宣传为新测出的公网加速结果。
