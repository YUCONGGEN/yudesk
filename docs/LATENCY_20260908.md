# 输入与画面响应追加优化（2026-09-08）

基线是 `20260908-compact-audio-v3` 的同源 Agent/Viewer。不是拿旧 Go 运行时与新运行时混比；本轮均使用 Go 1.27.1、同一 Windows i5-7300HQ（4 核）、本机加密中转和同一 Chromium。

## 改动

- 仅自适应模式在输入后 100ms 内使用短时采样，便宜的截图最快约 120Hz；按单次采集成本限制，较慢采集保持之前的约 60Hz 检查上限。固定帧率模式不变，原始图像队列仍最多 1 张，带宽及 ACK 在途限制不放宽。120Hz 是短时变化检查频率，不是保证传输 120FPS。
- 单区域文字/指针更新内联编码，避免为一个任务建立协程和通道；多区域继续使用最多 4 个有界 worker。合并载荷一次预分配，减少扩容和复制。
- Windows 原始 DIB 直接转为独占 RGBA 缓冲，两个像素一组处理；不再先原地转换、再整幅复制。不保留 GDI 指针，固定图像所有权和锁屏权限边界不变。
- 视觉测试增加慢样本的本机输入 HTTP 与画面响应时间明细，不输出访问令牌；可以区分本地发送、等待画面与浏览器呈现阶段。

## 两轮端到端模拟测量

同一脚本每档每轮预热 5 次后测 55 个样本。正常输入事件使合成 Agent 的指定像素改变；只有 Canvas 出现对应像素才结束计时。没有注入真实鼠标键盘。表中为两轮各自结果范围，**不能混成一次配对的加速百分比**。

| 注入 RTT 目标 | 基线 P50 | 优化 P50 | 基线 P95 | 优化 P95 |
| --- | --- | --- | --- | --- |
| 0ms | 21.8–24.8ms | 18.9–19.4ms | 41.2–67.4ms | 32.3–41.8ms |
| 40ms | 66.6–69.9ms | 62.3–64.8ms | 83.2–248.4ms | 144.9–197.5ms |
| 100ms | 120.7–121.6ms | 117.9–118.3ms | 152.9–293.8ms | 129.0–243.3ms |

正常响应中位数改善约几毫秒；尾部仍有波动，40ms 档不是所有分位都改善。基线最大值曾达 856ms，优化两轮最大为 309.2ms，但不能凭少量样本宣称长尾已消除。部分轮次探针 RTT 随负载升高（如优化 100ms 档末次为 143.5ms），仿真延迟目标不等于精确实际 RTT。

增加时序诊断后的额外基线：0ms 档 P50/P95 为 22.2/35.1ms，40ms 档为 64.8/82.7ms。这说明机器负载与重复轮次会显著影响尾部；没有隐藏较好的基线，也没有以最差基线来夸大收益。

Windows 1080p 内存转换微基准（各 3 次、400ms）：旧两遍处理约 6.69–8.76ms，新一遍分组处理约 4.62–4.95ms，均 0 次分配。频率和负载会影响这个区间。此测试不含 GDI 截屏、JPEG/PNG 编码、网络或物理显示器。

## 限制与下一步

不包含真实目标应用重绘、原生截图与显示器出光的合成响应测试，不能替代异地两台电脑实测；也未模拟丢包、带宽突降、4K 全屏视频或长时间负载。协议仍为端到端加密 TCP 的区域更新，不是 WebRTC 或原生硬件视频编码；公网 RTT、TCP 重传和共享文件流仍是约束。

进一步显著降低弱网/动态视频延迟需要分别验收原生采集/硬件编码和 UDP 媒体通道；本轮没有凭空开启新公网端口或放宽设备权限。测试和发布状态见 [RELEASE_STATUS](RELEASE_STATUS.md)。
