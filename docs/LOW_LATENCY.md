# 低延迟设计与验收（更新于 2026-09-12）

目标顺序：输入响应、画面时效、文字可读性、分辨率与帧率。目标 30 FPS 不是所有电脑和网络的性能保证。

## 研究与落地边界

查阅网络系统领域顶会的公开研究摘要及实时媒体标准：

- [Mowgli，NSDI 2025](https://www.usenix.org/conference/nsdi25/presentation/agarwal)：通过既有遥测日志训练实时视频码率控制模型，关注码率与卡顿。启示是先收集可靠运行指标再做学习控制；本项目没有相关训练集，当前没有部署或复现 Mowgli。
- [LoopTailor，NSDI 2025](https://www.usenix.org/conference/nsdi25/presentation/li-yang)：分析云游戏从输入到显示的完整交互链，减少 Android 图形流水线中的同步等待。本项目是桌面远控，不能直接套用 Android VSync 改造；借鉴的是减少串行等待、分清网络 RTT 和完整交互延迟。
- [RFC 8836](https://www.rfc-editor.org/rfc/rfc8836.html)：交互实时媒体与文件传输的目标不同，过晚的数据价值低，拥塞控制应兼顾时延。本实现采用有界在途量、合并旧区域、自适应退让；仍受到 TCP 重传和共享连接的约束。

这是基于上述原则的工程实现，不是“最新论文算法已全部实现”的声明，也不把传统区域差分包装成新的研究算法。

## 本版实现

1. 原始像素比较发生在编码前，未变化区域跳过编码。区域独立解码，适合界面和文字操作。
2. 浏览器直接解码 PNG/JPEG 小块并在 Canvas 合成，Go 控制端不解码再转码，不使用 base64。
3. 缓存每个区域的最新版本和版本号。浏览器显示完才请求下一批，按版本号取变化区域并集，避免浏览器解码缓慢时堆积旧画面，也避免只取最后一帧导致其他区域丢失。尺寸变化重建完整关键帧。
4. 输入改为有序单向事件。键盘、按下和松开不丢弃，只合并相邻移动。远端普通响应进入有界队列，释放输入读取循环；超时写入关闭整个连接以避免按键卡住。
5. 延迟优先默认档为 1280 最大宽度、30 FPS 目标、JPEG 70、8 Mbps 载荷预算。JPEG 画质不影响无损 PNG 区域。ACK RTT 增长或编码/写入成本过高时退让，稳定一段时间后缓慢恢复。
6. 本机 HTTP 监听与浏览器生命周期贯穿输入页、连接中和远控页。连接中关窗能取消中转等待；结束控制返回原窗口。
7. 状态查询即时使旧结果失效，提交校验不受定时刷新竞争影响；服务端区分管理在线与数据通道就绪，本机后端连接前复查。
8. 自适应模式收到输入后，前 100 毫秒按采集成本最高以 120 Hz 检查变化，随后保留到 350 毫秒、最高 60 Hz 的低成本尾段；固定模式仍遵守用户帧率。这样第一次采集若早于目标应用重绘，菜单、网页和动画的延迟重绘也能被及时捕获。带宽预算和 ACK 在途限制始终生效。
9. PNG 编码缓冲跨区域、跨帧复用，减少内存分配带来的 GC 抖动。同一合成 1080p 小区域更新基准，分配量从每次约 1,249,000 字节/48 次降到约 2,507 字节/18 次。CPU 耗时存在波动，不据此声称整体响应提速倍数。
10. 在途窗口由 ACK 的最低 RTT 基线计算：首次连接保守使用 2 帧，随后在 2～8 帧内按传播时延补足带宽时延积；字节窗口使用 20～150 毫秒的传播基线并限制在 8 KiB～1 MiB，不限带宽时为 128 KiB。平滑 RTT 高于基线的部分只作为排队信号，不能反向扩大窗口。单批可以超过字节阈值，但随后必须等待确认。
11. I/O 与 CPU 分工：独立采集 goroutine、容量为 1 的最新原始图像槽、有界区域编码 worker、原有独立输入读取及响应发送。等待带宽/ACK 不阻塞输入和采集；丢弃的是未编码原始图像，不是依赖链中的差分，编码器仍与上次实际编码的图像比较。
12. 区域编码最多使用 4 个 worker，多核机器预留调度余量；图像缓冲只在编码比较完成后归还采集端，不能覆盖正在使用的参考图像。复用缓冲池属于当前流，结束后释放；新增竞态、慢消费者、缓冲所有权和 ACK 队列边界回归。

## 可重复测试

```sh
go test -race ./...
go vet ./...
node --test scripts/input.test.cjs scripts/frames.test.cjs scripts/presence.test.cjs
go test -v ./internal/stream -run TestTiles -bench . -benchtime=200ms
go test -v ./cmd/yudesk-agent -run TestInputContinues
```

Windows 原生回归需设置 `YUDESK_CLIENT_DIR` 指向本轮编译的客户端目录，再运行 `cmd/yudesk-relay` 的 `TestNativeViewerExperience` 和 `TestNativeClientLifecycle`。浏览器回归由 `YUDESK_BROWSER_TEST_SCRIPT` 指定 `scripts/viewer-browser.test.cjs`，通过 `NODE_PATH` 提供 Playwright，并设置 `YUDESK_TEST_BROWSER`。

测试仅使用本机中转、临时身份和数据库；浏览器输入回归拦截输入请求，不对用户桌面执行随机点击。原生截图是真实桌面，但并非异地双机器的完整交互时延测试。

最终候选构建已通过 `go test -count=1 -race ./...`、`go vet ./...`、8 项 Node 回归和 Windows 原生体验/10 项进程生命周期回归。Windows 测试目标 30 FPS、960×540 实际桌面，首段实际接收 25.8 FPS、RTT 0.6 ms；浏览器交互阶段显示 15.4 FPS、RTT 21 ms。测试共新增 0 个可见 YuDesk 浏览器进程。该数据会随桌面变化、其他进程负载与采样区间变化，不是固定性能保证。Windows/Linux/macOS Intel/macOS Apple Silicon 均已编译，非 Windows 图形真机仍未验收。

合成 1920×1080 平坦桌面的一小块文字编辑：整屏 JPEG 33,647 字节，单区域 PNG 851 字节，载荷减少 97.5%。这是特定合成场景，不代表滚动、照片、视频等场景的平均收益。像素比较基准不包括原生屏幕采集，不应当作总耗时加速倍数。

## 操作到对应像素出现的测量

`TestNativeVisualLatency` 启动真实 Viewer、测试中转和使用同一会话/编码代码的合成 Agent。无界面 Chromium 发送正常鼠标移动事件，Agent 将收到的原始坐标编码成画面角落的颜色。只有控制端 Canvas 真正出现对应颜色才停止计时，不拿 RTT 或输入请求成功作为画面响应结果。测试不会注入操作系统输入，也不会打开可见测试窗口。

编译 `go test -c ./cmd/yudesk-agent` 为辅助测试程序；除前述浏览器与客户端环境变量外，将 `YUDESK_TEST_AGENT_HELPER` 指向它，`YUDESK_VISUAL_TEST_SCRIPT` 指向 `scripts/visual-latency.test.cjs`，然后运行 `go test ./cmd/yudesk-relay -run '^TestNativeVisualLatency$' -v`。测试用辅助进程仅存在于测试构建中，普通客户端没有合成桌面开关。

## 本轮校正：运行时与 I/O 链路

发行构建和 CI 改为固定 Go 1.27.1。原脚本固定 Go 1.22.12，其 Windows 定时精度会影响采集和模拟网络等待。[Go 1.23 官方说明](https://go.dev/doc/go1.23#time)记录了 Windows 定时器分辨率改进；同机原生探针 `TestNativeTimerResolution` 的实测如下（每档 60 次，不开 CPU 剖析）：

| 请求等待 | Go 1.22.12 P50 / P95 | Go 1.27.1 P50 / P95 |
| --- | --- | --- |
| 1 ms | 15.547 / 16.004 ms | 1.922 / 2.125 ms |
| 20 ms | 31.259 / 36.999 ms | 20.657 / 21.216 ms |

因此，上面旧版本表格的“额外往返延迟”只是注入目标，不是精确网络等待。不能把旧 40 ms 档与新 40 ms 档当成完全相同的网络条件计算提速比例。新测试额外记录实际应用层 RTT，并跳过已到期数据块的重复定时等待。

本轮另修复：

- 输入和小区域更新合并协议写入，加密记录头与密文一并写出。典型无二进制载荷的输入从 4 次、带小载荷的区域更新从 6 次底层 `Write` 调用降至 1 次；不改变线上的消息或密文格式，不把调用数等同于 IP 包数。大载荷仍分块，避免额外复制整份大文件。
- 单帧 HTTP 响应声明准确长度，浏览器消费到 EOF 后复用连接；成功绘制不再取消未结束的分块响应。仍是一帧画完才请求下一批，保持慢消费者合并策略。
- 画面缓存快照仅在锁内选取不可变区域引用，排序和大块拼接移至锁外；预分配拼接缓冲。
- 累计区域缓存设 32 MiB 上限，拒绝超限更新时保留原有一致状态，避免单批合法但累计无界的缓存。

Go 1.27.1 候选构建，两轮合成视觉响应复测，每档每轮 55 个有效样本、无 CPU 剖析：

| 额外 RTT 目标 | 末次 RTT 探针 | 响应 P50 | 响应 P95 | 最大响应 |
| --- | --- | --- | --- | --- |
| 0 ms | 约 0 ms（四舍五入） | 21.2～22.6 ms | 35.4～37.8 ms | 39.6～43.4 ms |
| 40 ms | 41.5～42.0 ms | 64.9～67.0 ms | 107.3～143.8 ms | 137.1～265.1 ms |
| 100 ms | 101.2～101.6 ms | 118.6～120.1 ms | 132.0～134.8 ms | 136.2～136.7 ms |

本机中位数和短等待有所改善，但 40 ms 档仍有约 265 ms 的尾部异常，未消除全部卡顿，不能作为公网稳定近同步的验收。原生 Windows 回归首段 960×540、目标 30 FPS，实际收到 28.0 FPS、RTT 0.6 ms；浏览器操作/改设置后的采样为 24.9 FPS、RTT 105 ms。这些区间不能直接互相比较。

本轮全量竞态与静态检查、9 项 Node 回归、Windows 原生体验与 10 项生命周期测试通过，新增可见 YuDesk 浏览器进程为 0。新 Viewer 与旧 Go 1.22 Agent 测试辅助程序、旧 Viewer 与新 Agent 测试辅助程序均通过实际协议互通测试。四个平台已重编译，但未更新公网服务或下载文件。

随后将远程画面和黑边统一为系统箭头，移除遗留十字光标样式；重新构建四个平台并通过 Windows 原生体验测试及无界面浏览器的普通、拖动、仅观看样式、全屏光标检查。光标由本地系统显示，不等待远端画面，也不修改被控端的系统指针设置。macOS/Linux 共享此样式，但尚未在对应系统上做实机光标验收。

## 2026-09-12：外网窗口与会议实时媒体

- 桌面区域流、桌面完整 JPEG 兼容流和 Android 被控端统一使用 RTT 自适应在途帧窗口。低 RTT 不再沿用固定约 100 毫秒的积压；约 100 毫秒外网又能保留约 3 帧，避免固定 2 帧把 30 FPS 人为限制到约 20 FPS。
- 窗口只使用最低 ACK RTT 作为传播基线；当前平滑 RTT 的增长继续触发画质/分辨率退让，不会扩大窗口。捕获、输入、编码和网络仍是独立的有界工作链。
- 浏览器与 Android 会议根据参会连接数、候选链路 RTT 和 WebRTC `availableOutgoingBitrate` 为每个视频发送器设置上限，并使用 `maintain-framerate`，拥塞时优先降清晰度保交互连续性。屏幕共享和摄像头分别使用独立预算，突发低带宽允许进入应急低码率，而不是继续制造发送队列。
- 浏览器给语音、摄像头和屏幕轨道分别设置 `speech`、`motion`、`detail` 内容提示；Android 开启低延迟音频、抖动缓冲快速追赶、DSCP 和 CPU 过载检测，语音发送优先于视频。会议状态显示实际候选链路 RTT。
- Android 屏幕共享目标提高到 30 FPS；四 ABI 的 gomobile 核心重新生成后，通过三轮竞态测试、Java 单元测试、Lint、APK 签名与 16 KiB 对齐验证。

本轮 Windows 合成端到端视觉回归每档 55 个样本，测量从输入事件到匹配像素实际出现在 Canvas，而不是只测请求返回：

| 注入 RTT 目标 | 实测 RTT | 响应 P50 | 响应 P95 | 最大响应 |
| --- | --- | --- | --- | --- |
| 0 ms | 18.5 ms | 23.6 ms | 54.3 ms | 77.1 ms |
| 40 ms | 42.0 ms | 64.7 ms | 82.6 ms | 91.5 ms |
| 100 ms | 102.3 ms | 119.4 ms | 130.9 ms | 132.6 ms |

该测试是稳定延迟的合成桌面，不模拟公网丢包、抖动、目标应用重绘和物理显示器出光；会议码率策略已做浏览器/Android 单元及构建验证，仍需不同运营商双真机长时间测试来建立会议 P95 指标。

## 仍需完成的高性能路线

- Windows DXGI/WGC + 硬件 H.264，macOS ScreenCaptureKit/VideoToolbox，Linux PipeWire/VAAPI；目前 Windows 仍用 GDI，Linux/macOS 仍有外部截图工具开销。
- 视频用 WebRTC/UDP，可靠按键和低可靠移动通道分别调度；中转部署需实际验证公网 UDP、认证、防滥用和禁用设备时的会话撤销。
- 丢包、抖动、带宽骤降、4K 大面积变化、文件并发传输、系统音频等场景的跨机器 P50/P95 输入到画面响应测量。
- 现在的 TCP 通道仍有重传及大文件共享写入的限制，全屏视频不是该区域编码器的优势；不能保证 ToDesk 同等延迟或“永不卡”。

网站继续使用 HTTP 8235；现有会话继续使用验证指纹的 TLS 8233 和 Agent ↔ Viewer 端到端加密。此次没有开启新的公网端口。
